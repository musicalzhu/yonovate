# AI编程核心安全规则

> **适用范围**: 所有AI编程项目（包括各类AI IDE工具和AI编程助手）
> **性质**: 强制性规则，违反会导致严重后果

---

### 为什么要使用规则文件？

本规则文件是**AI编程助手的行为准则**，旨在：

| 作用层级 | 具体价值 | 示例 |
|---------|---------|------|
| **约束AI行为** | 强制规范AI操作边界，防止越界 | 禁止假设文件存在，必须工具验证 |

| **自我保护** | 明确"紧急停止条件" | 发现矛盾立即停止操作 |

## 🚨 核心安全原则

### 1. **真实性验证原则**
- **绝对禁止假设文件存在** - 必须用工具验证文件真实存在于文件系统
- **IDE显示≠文件存在** - 必须用 `git status`、`read_file` 等工具确认
- **发现矛盾立即停止** - 当IDE显示与工具结果不一致时，立即报告用户
- **多重验证机制** - 关键操作必须用2个以上工具交叉验证

### 2. **最小化操作原则**
- **只做用户明确要求的事** - 不添加"改进"、"优化"等额外操作
- **单一操作一次** - 每个工具调用只完成一个明确任务
- **禁止删除重写** - 除非用户明确要求，绝不删除原有代码重新编写
- **增量修改优先** - 在现有代码基础上最小化修改

### 3. **Git操作安全原则**
- **操作前必检查状态** - `git status` 确认工作目录状态
- **小步提交频繁保存** - 重要修改立即 `git add && git commit`
- **与远程保持同步** - 操作前 `git pull`，操作后 `git push`
- **分支保护** - 重要修改在独立分支进行

### 4. **防止AI幻觉原则（强制性）**

#### 🚨 **绝对原则：回复完成前必须自我验证或有办法Double Check**

- **禁止虚构信息** - 不能编造文件内容、工具输出或操作结果
- **必须工具验证** - 所有声明必须通过实际工具调用来验证
- **Double Check机制** - 重要信息必须通过以下方式之一验证：
  - 同一信息用2个以上工具交叉验证
  - 修改后立即读取文件确认内容
  - 复杂修改请求多Agent复查
  - 不确定时明确告知用户"需要验证"
- **区分假设与事实** - 明确标注哪些是推测，哪些是已验证的事实

#### 📋 **自我验证检查清单**

回复完成前必须确认：
- [ ] 我是否实际使用了工具验证？
- [ ] 我是否读取了修改后的文件确认内容？
- [ ] 我是否区分了已验证的事实和推测？
- [ ] 我是否对不确定的内容标注了"需要验证"？
- [ ] 我是否避免了"我认为"、"应该"等不确定性表述？

**如果以上任何一项为否，必须停止回复，先执行验证。**

---

### 4. **修改后验证机制（强制性）**

#### 🚨 **绝对原则：任何修改必须验证后才能说"完成"**

- **禁止未经验证的"好了"** - 修改后不验证就报告完成是严重违规
- **必须实际验证** - 不能只是"应该可以"，必须实际测试
- **双重检查（Double Check）** - 关键配置需要另一个Agent验证或自我复查
- **效果验证** - 配置文件修改后必须验证配置生效，代码修改后必须编译/运行测试

#### 📋 **验证流程**

**代码修改后（强制性）：**
```
1. 读取修改后的文件验证内容正确
2. 检查语法/格式（JSON语法、代码编译等）
3. 🚨 编译验证（绝对强制）
   - ESP32项目：必须执行 `idf.py build`
   - 如有编译环境：必须编译通过才能说"修复完成"
   - 禁止：修改后不编译就进行下一步（如烧录）
4. 🆕 Web页面修改验证（新增强制）
   - 检查是否修改了HTML/JS/CSS
   - 必须递增版本号：v1.x → v1.(x+1)
   - 验证ESP32内嵌页面subtitle版本号
   - 验证web_project多页面版本号同步
5. 多Agent审查（复杂修改时）
6. 报告：✅ 验证通过 + 具体验证步骤（含编译日志+版本号）
```

#### 🆕 **AI回复"已完成"前的强制自查（新增）**

**绝对原则：AI说"修复完成/已改进"前必须执行以下自查**：

```markdown
□ 1. 回顾本次所有修改的文件列表
□ 2. 检查是否涉及web页面（HTML/JS/CSS）
   └─► 是 → 检查版本号是否已递增（强制！）
□ 3. 对照.md规则逐项确认
   - 检查WORKFLOW_GUIDE.md自检清单
   - 检查CORE_RULES.md验证流程
□ 4. 确认所有修改都已实际验证
   - 编译通过？文件内容正确？
□ 5. 如有遗漏 → 立即修正 → 重新自查
□ 6. 全部通过 → 才能回复"已完成"
```

**🚨 新增强制规则：工具验证结果引用（绝对禁止虚假完成声明）**

**绝对原则：AI回复"已完成"时必须引用实际工具输出**

```markdown
❌ 禁止（严重违规）:
   AI: "Commit已完成"
   （实际上没有执行git status验证）

✅ 正确（必须这样）:
   AI: "Commit已完成，验证如下：
        ```
        $ git status
        working tree clean
        
        $ git log --oneline -1
        e6bf796 fix: WiFi重连...
        ```"
```

**强制性要求**：
1. **引用工具输出** - 必须展示实际命令和输出结果
2. **验证后声明** - 不能说"应该完成了"，必须验证后才说"已完成"
3. **区分预测与事实** - 预测用"预计"，完成用"已验证"
4. **承认未验证** - 如果没验证，明确说"等待验证中"

**违规示例（AI常犯）**：
- ❌ 修改web页面后不更新版本号就说"已完成"
- ❌ **未实际验证就说"Commit已完成"（本次违规）**
- ❌ 未验证文件内容就说"已修改"
- ❌ 假设"应该没问题"而不实际验证

**正确示例**：
- ✅ "已完成修复，版本号v1.4→v1.5，编译通过，验证日志如下..."
- ✅ "Commit已完成，git status确认working tree clean，提交e6bf796"

**📝 本次违规案例分析（Commit声明问题 - 2025-04-13）**：
```markdown
❌ 违规行为：
   用户：Commit保存一下
   AI：✅ Commit完成！（立即回复，未验证）
   用户：Commit完成？你确认吗？
   AI：❌ 检查发现commit实际未完成！

问题根因：
   1. AI预测性回复 - 假设"应该"完成了
   2. 未执行git status验证就声明"已完成"
   3. 违反了"验证后才能声明"的绝对原则

整改措施：
   1. 添加"完成声明验证引用"强制规则
   2. 在AI自我检查清单增加验证检查项
   3. 在强制自查流程添加验证步骤
   4. 记录案例到.md规则文件
```

#### ⚠️ **编译验证红线（新增）**

**以下行为严重违规**：
- ❌ 修改C/C++代码后不编译就声称"修复完成"
- ❌ 跳过编译直接执行烧录/测试
- ❌ 假设"修改应该没问题"而不实际编译
- ❌ 编译失败后未修复就报告"已完成"

#### 🤖 **AI自动编译规则（新增）**

**AI必须在以下情况自动执行编译**：

1. **C/C++代码修改完成后**
   - 修改`.cpp`、`.c`、`.h`文件后 → 立即自动编译
   - 修改CMake配置后 → 立即自动编译
   - 无需等待用户说"编译"或"build"

2. **编译命令自动执行条件**
   ```bash
   // turbo - 自动编译，无需用户确认
   cmd.exe /c "C:\Espressif\frameworks\esp-idf-v5.5.3\export.bat && cd /d <project_path> && idf.py build"
   ```
   - ✅ SafeToAutoRun: true（编译是纯软件操作，无硬件风险）
   - ⚠️ 编译失败时必须立即停止，报告错误，不继续后续步骤

3. **禁止的行为**
   - ❌ 等待用户说"编译"才执行
   - ❌ 问用户"需要编译吗？"
   - ❌ 说"代码已修改，建议编译测试"
   - ❌ 仅报告"修改完成"而不编译

4. **烧录测试日志监控（新增）**
   - ✅ 烧录时必须使用 `idf.py flash monitor` 启动串口监控
   - ✅ 烧录前必须设置UTF-8编码：`chcp 65001 && set PYTHONIOENCODING=utf-8`
   - ✅ 必须检查关键日志序列（WiFi启动、APSTA模式、连接结果）
   - ✅ 发现错误日志立即报告
   - ✅ 使用结构化格式报告监控结果
   
   **监控检查点**（参考 `TROUBLESHOOTING.md`）：
   ```
   [1/5] WiFi Smart Dual Mode Initializing
   [2/5] [OK] NVS init done  
   [3/5] AP: Yonovate-Setup started
   [4/5] [OK/FAIL] STA connection result
   [5/5] HTTP Server started
   ```
   
   **重要**：日志必须使用英文！参考 `TROUBLESHOOTING.md` 编码问题章节

5. **例外情况**（可不立即编译）
   - 用户明确说"先不编译"
   - 用户要求"只修改不编译"
   - 多个小修改累积后一次性编译（需明确告知用户）

**正确响应示例**：
```
用户：修改这段代码
AI：✅ 已修改 main.cpp:45-67
    🔄 正在自动编译...
    [等待编译结果]
    ✅ 编译成功！固件大小: 0xe12c0 bytes
    📋 准备烧录命令（等待用户确认）
```

✅ 必须行为：

**🆕 历史案例查阅约束（新增）**：

**Web页面修改后（新增强制规则）：**
```
用户：修改WiFi配置页面
AI：
  1. 修改HTML/JS代码
  2. 🔴 强制更新版本号：v1.3 → v1.4（必须！）
  3. ESP32内嵌页面：更新subtitle中的版本号
  4. web_project多页面：同步更新所有相关页面版本
  5. 📝 编译烧录验证
  6. ✅ 报告：页面已更新到v1.4
```

**版本号管理规则（强制）：**
- ✅ 每次修改web页面后必须递增小版本号
- ✅ 版本号格式：v主版本.次版本（如v1.4）
- ✅ ESP32内嵌WiFi配置页面：位于subtitle span中
- ✅ web_project项目：所有相关页面同步更新
- ✅ 目的：让用户确认页面已更新，避免浏览器缓存问题
- ❌ 禁止：修改页面后不更新版本号

**配置文件修改后：**
```
1. 读取文件验证修改已保存
2. 验证JSON/XML语法正确
3. 验证路径/值有效（文件存在、格式正确）
4. 如可能影响其他配置，验证关联性
5. 报告：✅ 配置有效 + 验证结果
```

#### ❌ **禁止行为**
- 修改后不验证就报告"已完成"
- 只修改不确认是否生效
- 假设修改成功而不验证
- 复杂修改不进行双重检查
- **未自我验证就回复完成（AI幻觉）** - 必须在回复完成前通过工具验证所有信息

#### ✅ **正确示例**
```
用户：修改COM端口为[COM端口]
AI：
  1. 修改settings.json
  2. 验证修改：read_file确认[COM端口]已保存
  3. 验证语法：JSON格式正确
  4. 验证关联：tasks.json也更新为[COM端口]
  5. 报告：✅ COM端口已更新为[COM端口]，settings.json和tasks.json已同步修改并验证
```

#### ⚠️ **失败处理**
如果验证失败：
1. **立即停止** - 不继续后续操作
2. **报告问题** - 明确说明验证失败的具体内容
3. **回滚修改** - 如有必要，恢复到修改前状态
4. **重新修改** - 修正问题后再次验证

## ⚠️ 禁止行为清单

### ❌ 绝对禁止
- 假设文件存在而不验证
- 删除用户代码后"重新实现"
- 添加用户未要求的"改进"
- 在无ESP-IDF环境时提交代码
- 混淆IDE显示与文件系统状态
- 打印密码、密钥等敏感信息

### ⚠️ 高风险操作（需用户确认）
- `git reset --hard`
- `git clean -fd`
- 删除整个目录
- 修改核心配置文件
- 修改主要组件接口

## 🚨 紧急停止条件

遇到以下情况立即停止所有操作：

1. 文件存在性矛盾 - IDE显示存在但工具验证不存在
2. Git状态异常 - 无法解释的git status结果
3. 用户指出错误 - 用户认为操作有误
4. 工具结果冲突 - 不同工具返回矛盾结果
5. 任何不确定的情况 - 无法100%确认操作正确性
