# 规则文件维护指南

> **用途**：指导AI如何维护、更新和补充规则文件
> **性质**：当遇到新问题、新约束、新规则时，必须遵循此指南进行归档

---

## 📋 规则维护原则

### 1. 通用化原则（强制）

**所有特定信息必须改为通用形式**，确保规则可跨环境使用：

| 信息类型 | 特定信息示例 | 通用形式 | 适用文件 |
|---------|-------------|---------|---------|
| **用户名** | `Tom`, `User123` | `[用户名]` | 所有规则文件 |
| **项目路径** | `c:\Downloads\code-v2\v2` | `[项目根目录]` | 所有规则文件 |
| **硬件端口** | `COM5`, `/dev/ttyUSB0` | `[COM端口]` | ESP32相关规则 |
| **安装路径** | `C:\Espressif\frameworks\esp-idf-v5.5.3` | `[ESP-IDF安装路径]` | ESP32相关规则 |
| **IP地址** | `192.168.1.100` | `[IP地址]` | 网络相关规则 |
| **域名/URL** | `github.com/musicalzhu` | `[仓库地址]` | Git相关规则 |
| **AI工具名称** | `Windsurf`, `Cursor` | `[AI工具]` | 通用规则 |
| **版本号** | `v5.5.3` | `[版本号]` | 可选保留具体版本 |

**禁止行为**：
- ❌ 记录具体用户名、个人路径
- ❌ 记录特定IDE或工具名称（除非作为示例）
- ❌ 记录特定硬件端口号
- ❌ 记录实际IP地址或域名

**正确做法**：
- ✅ 使用`[占位符]`表示可变信息
- ✅ 添加注释说明占位符含义
- ✅ 提供示例值但不作为强制要求

## 🗂️ 规则分类与归档

### 规则文件分类体系

遇到新问题时，按以下分类归档到对应文件：

| 问题类型 | 归档文件 | 内容示例 |
|---------|---------|---------|
| **安全原则**<br>（验证、禁止行为） | `CORE_RULES.md` | 真实性验证原则、最小化操作 |
| **技术规范**<br>（编码标准、最佳实践） | `ESP32_STANDARDS.md` | 内存管理、错误处理、GPIO规范 |
| **操作流程**<br>（执行步骤、检查清单） | `WORKFLOW_GUIDE.md` | Git提交流程、编译验证步骤 |
| **问题排查**<br>（故障诊断、解决方案） | `WORKFLOW_GUIDE.md` | Windows Git问题、编译错误 |
| **规则维护**<br>（如何更新规则） | `RULE_MAINTENANCE.md` | 本文件 |

### 新增规则归档流程

```
1. 识别问题/约束/规则类型
   ↓
2. 选择对应的目标文件
   ↓
3. 编写通用化描述（使用[占位符]）
   ↓
4. 更新CR_HISTORY.md记录变更
   ↓
5. 验证内容已正确归档
```

## 🔄 规则更新流程

### 发现问题时自动归档

当对话中识别到新问题/约束时，AI必须：

1. **立即判断问题类型**
   - 安全类 → CORE_RULES.md
   - 技术类 → ESP32_STANDARDS.md
   - 流程/问题类 → WORKFLOW_GUIDE.md

2. **编写通用化内容**
   - 将所有特定信息替换为`[占位符]`
   - 添加注释说明占位符含义
   - 确保描述不依赖特定环境

3. **选择合适位置**
   - 安全原则 → CORE_RULES.md 对应章节
   - 技术规范 → ESP32_STANDARDS.md 对应技术领域
   - 问题排查 → WORKFLOW_GUIDE.md "常见问题"章节

4. **更新CR_HISTORY.md**
   ```markdown
   ### 规则文件更新（日期）
   **文件**: `[目标文件]`
   **更新内容**: [简要描述]
   - 新增/修改章节: [章节名]
   - 解决的问题: [问题描述]
   - 通用化处理: [如何通用化]
   ```

5. **验证归档**
   - 读取目标文件确认内容已添加
   - 检查通用化是否彻底
   - 确认CR_HISTORY已更新

### 维护检查清单

每次更新规则文件时必须检查：

- [ ] 所有特定信息已通用化
- [ ] 使用`[占位符]`标注可变信息
- [ ] 添加了注释说明占位符含义
- [ ] 内容归类到正确的文件
- [ ] CR_HISTORY.md已同步更新
- [ ] 格式符合Markdown规范
- [ ] 无拼写或语法错误
- [ ] 便于其他AI理解和使用

## 🎯 示例：自动维护流程

### 场景：发现新的Git问题

**用户**: "git push时提示权限不足"

**AI识别**: 这是Git操作流程问题，需要归档到WORKFLOW_GUIDE.md

**AI执行**:
```
1. 分析根本原因：SSH密钥配置问题
2. 编写通用化内容：
   - "github.com/musicalzhu" → "[仓库地址]"
   - "C:\Users\Tom\.ssh" → "[SSH目录]"
3. 添加到WORKFLOW_GUIDE.md "常见问题"章节
4. 更新CR_HISTORY.md记录
5. 报告用户：已归档到规则文件
```

**归档内容示例**:
```markdown
#### ⚠️ Git权限问题 - push失败

**问题现象**: git push时提示权限不足
```
Permission denied (publickey).
fatal: Could not read from remote repository.
```

**根本原因**: SSH密钥未配置或配置错误

**识别方法**:
```bash
# 测试SSH连接
ssh -T git@[仓库地址]
```

**解决方案**:
```bash
# 方法1: 生成SSH密钥
ssh-keygen -t ed25519 -C "[邮箱]"

# 方法2: 添加密钥到ssh-agent
ssh-add [SSH目录]/id_ed25519

# 方法3: 在[代码托管平台]添加公钥
cat [SSH目录]/id_ed25519.pub
```

**验证修复**:
```bash
ssh -T git@[仓库地址]
# 应显示: Hi [用户名]! You've successfully authenticated...
```
```
